---
name: Batch and Full Run
description: Batch generation and whole-dataset execution have distinct workflows and stop rules.
---

**Run Whole Dataset** starts a full run for one selected side. `/api/fullrun/run` validates the dataset and side, rejects a duplicate run for that same dataset and side, then launches `fullrun_worker`. Primary and validation have separate run state, output, and input code; running one side does not start the other. Batch's whole-dataset option is different: after its generation and comparison steps succeed, it starts full runs for primary and validation independently and waits for both.

`fullrun_plan` orders work as dataset keys first, dataset-level variables next, then each parameter layer's Records node followed by that layer's variables in parameter-DAG order. Dataset-level and within-layer variables follow graph topological order. `fullrun_steps` exposes coded steps; the generated program in `fullrun_program_text` runs them, and layered datasets use `fullrun_layered_program_text`.

An execution error stops the remaining work that depends on the failed item. Those items are recorded as skipped with reasons such as `upstream X not run`; independent items continue. In a parameter layer, a failed variable blocks its dependents, while independent variables in that layer can still run. A failed Records step prevents that layer's variables from running. Missing code is marked `no code` and dependent items are skipped. Non-layered runs stop the execution sequence on the first failure and mark remaining items as upstream-not-run, no-code, or `not run after X failed`.

Full Run checks that dataset-level results include the subject key and target, and rejects duplicate subject keys when the target is `USUBJID`. Records output must include dataset keys and `PARAMCD`; `PARAMCD` must be allowed for that layer, and dataset keys plus `PARAMCD` must be unique. Variable results must include their keys and target, contain no keys outside the key dataset, and preserve its row count when merged. A successful result is saved as `result.rds`. `fullrun_worker` writes `run.json` with status, timestamps and duration, completed and skipped items, failure and not-run reasons, row and column counts, code hashes, and partial-run information. It also writes `program.R` and `log.txt` under the project's `.dualdag/fullrun/<dataset>/<side>/` directory. `/api/fullrun/status` returns the run metadata, running and stale flags, log tail, and readiness; `/api/fullrun/program` and `/api/fullrun/log` expose the generated program and log.

`batch_order_for` places keys first, then dataset variables, then Records and parameter variables layer by layer in parameter-DAG order. `batch_advance` generates both sides for each node, and `batch_after_generate` records generation or comparison outcomes. A regular selected-node Batch records a failure and continues to later nodes. A Run Whole Dataset batch sets `stop_on_error`: a generation or comparison failure stops the batch before later nodes and prevents its full runs from starting. If generation and comparison finish without a stop, `batch_start_fullruns` starts primary and validation full runs independently, even if one side's full run fails.
